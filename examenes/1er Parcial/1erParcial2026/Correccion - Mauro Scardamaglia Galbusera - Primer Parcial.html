1.a — Problemas de diseño

Transcripción

Los problemas de diseño de la solución actual son redundancia innecesaria, duplicación de código y alto acoplamiento.

Los preparadores tienen métodos idénticos que se podrían generalizar en una clase padre, tienen una secuencia de pasos que deben cumplir en cada clase, esto también se puede generalizar al padre.

Y la creación de los preparadores es un proceso engorroso que se repite, y podría ser delegado a una clase que se encargue de eso (Patrón Factory).

Descuentos

  • -0.2: no menciona el problema del procedimiento de preparación: solo señala que los métodos y la secuencia de pasos se repiten en cada clase, pero no dice que, al estar preparar en una interfaz, cada clase puede alterar el orden de los pasos o implementarlo como quiera.

1.c — Método template y operación de utilitarios

Transcripción

public void final preparar (Vehiculo v) {
    VerificarDocumentacion (v);
    limpiar (v);
    ajustarPresion (v);
    hook (v);
    registrarEvento (v);
}

Este es el patrón Template Method con Hook.
El método que no debe poder ser redefinido es preparar() que indica la secuencia de pasos, el resto puede ser redefinido, ajustarPresion () debe ser redefinido porque depende de c/ vehículo, el "método variable" es el hook() que permite a utilitarios agregar un accesorio, en caso contrario no hace nada.

1.e — Patrones de diseño

Transcripción

Utilicé Template Method con Hook para la secuencia de pasos para preparar un vehículo para alquiler, el hook permite agregar accesorios. Esto resuelve el problema de duplicación de código y alto acoplamiento para la secuencia de pasos.

Utilicé Patrón Factory para la creación del preparador concreto, se centraliza esta operación en una clase con esta responsabilidad y se evita códigos grandes con ifs en muchas partes y como en el caso anterior, se evita alto acoplamiento.
